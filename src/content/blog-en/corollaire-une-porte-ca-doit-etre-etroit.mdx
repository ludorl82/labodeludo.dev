## What pass through the door: JSON-RPC, and not much else

An MCP server, seen from outside, is one single address, `/mcp`. The client (the Claude app, Home Assistant, anybody) send there a POST that contain a [JSON-RPC 2.0](https://www.jsonrpc.org/specification) message: a method, parameters and an identifier. The server answer with the same identifier. That's all.

The first message is called `initialize`. Here is the real one, sent with curl to the public server of the articles (the server speak French, it is a Québec lab):

```
$ curl -s https://articles.labodeludo.dev/mcp \
    -H 'Content-Type: application/json' \
    -H 'Accept: application/json, text/event-stream' \
    -d '{"jsonrpc":"2.0","id":1,"method":"initialize","params":{"protocolVersion":"2025-11-25","capabilities":{},"clientInfo":{"name":"curl","version":"0"}}}'
{"jsonrpc": "2.0", "id": 1, "result": {"protocolVersion": "2025-11-25",
 "capabilities": {"tools": {"listChanged": false}},
 "serverInfo": {"name": "articles", "title": "Articles du labo", "version": "1.0.0"},
 "instructions": "Les articles du blogue labodeludo.dev, le labo de Ludo : chercher un passage, lire un article, lister les derniers parus. [...]"}}
```

The server say which version of the protocol he speak, that he has tools, and he give `instructions`: a paragraph that the client hand to the model. After come `tools/list`, which return the list of tools with their descriptions, and `tools/call`, which call one.

The [specification of the "Streamable HTTP" transport](https://modelcontextprotocol.io/specification/2025-11-25/basic/transports) leave to the server the choice to answer with a simple JSON object or to open an SSE stream to send many messages. Our servers always take the simple road. It also say that a server who offer no stream must answer 405 to a GET. Ours do it:

```
$ curl -s -o /dev/null -w '%{http_code}\n' https://articles.labodeludo.dev/mcp
405
```

Finally, the specification let the server keep no session at all: the `MCP-Session-Id` header is optional. We don't emit one. Each request stand on its own, which mean a pod can restart in the middle of a conversation and nobody notice.

All the logic of the protocol fit in one function, `handle()`. Here is the heart of the hockey one, taken from the [public repository](https://github.com/ludorl82/mcp-servers):

```python
if method == "initialize":
    asked = params.get("protocolVersion")
    return ok({
        "protocolVersion": asked if asked in PROTOCOLS else PROTOCOLS[0],
        "capabilities": {"tools": {"listChanged": False}},
        "serverInfo": {"name": "hockey", "title": "Hockey canadien", "version": "2.0.0"},
        "instructions": INSTRUCTIONS,
    })
if method == "ping":
    return ok({})
if method == "tools/list":
    return ok({"tools": [spec for _, spec in TOOLS.values()]})
if method == "tools/call":
    tool = TOOLS.get(params.get("name"))
    if not tool:
        return err(-32602, f"Outil inconnu : {params.get('name')}")
    ...
    return ok({"content": [{"type": "text", "text": text}], "isError": is_error})
return err(-32601, f"Méthode inconnue : {method}")
```

Those thirty lines are copied in each of the three files. Copy-paste the same code three times, usually, it get you slapped on the fingers in review. Here, it is on purpose: each server start with `python3 -I`, the isolated mode, which don't add the folder of the script to the module path. A shared module would simply not import. One file, one official Python image, no `pip install` at startup: you copy the file somewhere else, and it run.

## The description, it is the prompt

Here is what the model receive to decide if he call `match_lnh` (in French in the code, translated here):

```python
"description": "The game of a Canadian NHL team right now: live score, period, "
               "time left, shots, who scored and who got assists. If no game is "
               "in progress, the last result and the next game. For 'what's the score?'.",
```

The model don't see the code. He see this sentence, the schema of the parameters, and nothing else. The last part, "For 'what's the score?'", is not documentation for a human: it is an example of the sentence Ludo will say, put there so the model make the link. When a description is blurry, the model pick the wrong tool or fill the parameters badly, and this is not a bug you find with a debugger.

The output count as much as the input. The [tools specification](https://modelcontextprotocol.io/specification/2025-11-25/server/tools#error-handling) separate two kinds of errors. Protocol errors (unknown tool, malformed request) are JSON-RPC errors, and the client is not obliged to show them to the model. Execution errors (an API down, an invalid parameter) come back in a normal result with `isError: true`, and the specification say they must contain enough for the model to correct himself. The hockey server do it when you ask him for a team that don't exist (translated):

```python
text = (f"“{e}” is not a Canadian NHL team. I know the Canadiens, "
        "the Maple Leafs, the Senators, the Jets, the Flames, the Oilers and the Canucks.")
```

With that, the model has what he need to recover alone: he read the list again, understand that the Nordiques are not coming back, and ask again with a real team. It is exactly what was missing on October 23, when Radar was restarting. The message before said "Radar is not responding right now (namespace radar)." The model could not know if it was the cluster or the tool, so he asked Ludo if he shut down vega anyway. The message after say what happen most often, how long it last, what it does not mean, and what to do instead. Four pieces of information, zero debugger.

## A door for the ear

The servers answer in sentences, never in tables or raw JSON, because the answer often end up read out loud. A model can rephrase a table, but he do it badly, and by voice he do it slowly.

The images, that's another story. labo-mcp has a tool `maison_camera`, which return a picture from a camera of the house in an MCP `image` block. On October 22, in text mode, Claude in the app said he was receiving the image, but could not see what was in it.

I accused the Claude app. The Claude app had done nothing.

The JPEG of the camera contained a comment segment full of zeros whose announced length was wrong: 4,094 bytes announced, 4,958 real. Web browsers look for the next marker and show the image anyway, which explain why the picture looked perfect in Home Assistant. The Claude API, her, refused the image with "Could not process image". I would have known right away if I had first tried to read the image myself instead of suspecting the client. The fix, `jpeg_propre`, skip every comment segment up to the next real marker and touch nothing else: the image go from 33,708 to 28,748 bytes, and Claude see it.

There is still a real limit, which is not a bug: in voice mode, the app show the image on the screen, but the model don't receive it. For the ear, a tool must return text. A door for the voice, it is a door that talk.

## The public door: narrow by construction

The three public servers (hockey, weather, articles) have no secret to keep. They read public sources or the blog itself, keep nothing, write nothing. Their narrowness, it is what they don't have: no token, no access to the lab, no write.

There is still the cost. The [tools specification](https://modelcontextprotocol.io/specification/2025-11-25/server/tools#security-considerations) ask servers to rate limit the calls. For the articles, each search make a graphics card of the server bob compute a vector, with the bge-m3 model. A [Cloudflare rate limiting rule](https://developers.cloudflare.com/waf/rate-limiting-rules/) block so an IP address that go over 30 requests in 10 seconds, for 10 seconds. The day we put it in place, I fired 40 quick requests at the public address: 32 answers 200, then 8 answers 429. The count is not exactly 30 because Cloudflare count per data center and catch up with a small delay, which its documentation admit. It is a brake, not a wall, and that's all we need here.

Ludo, he advertise only this address. The others exist, but an advertised address is a promise, and Ludo did the math: he will not promise the hockey to the whole world.

## The private door: an OAuth server who remember nobody

labo-mcp, him, has things to guard: the private repositories of Ludo, the state of the lab, the house. It need a lock.

The reflex of Ludo was Cloudflare Access, which already guard his other private services. What I saw is that the Claude app don't get through Access in front of an MCP endpoint: she follow the authorization flow of the [MCP specification](https://modelcontextprotocol.io/specification/2025-11-25/basic/authorization), based on OAuth 2.1, and expect to do it herself. So labo-mcp became his own authorization server. Here is the flow, in the order the app walk through it.

1. **The refusal that guide.** The app call `/mcp` without a token. The server answer 401 with a `WWW-Authenticate` header that point to `/.well-known/oauth-protected-resource`. This document, defined by [RFC 9728](https://datatracker.ietf.org/doc/html/rfc9728), say where is the authorization server. Here, it is the same server.
2. **The registration.** The app register itself at `/register`, by [dynamic registration](https://datatracker.ietf.org/doc/html/rfc7591). The November 2025 specification keep this mode for compatibility and recommend another one, but it's the one the app used with us. `/register` refuse every redirect address that is not Claude's (claude.ai, claude.com, and localhost for Claude Code).
3. **The only human page.** The app open `/authorize` in Ludo's browser. This one, Cloudflare Access guard it: you need the code received by email. And the server don't just watch Access go by. He [validate himself the token](https://developers.cloudflare.com/cloudflare-one/access-controls/applications/http-apps/authorization-cookie/validating-json/) that Access add in the `Cf-Access-Jwt-Assertion` header: RS256 signature against the public keys of the team, audience, issuer, email.
4. **PKCE.** The app send a `code_challenge`; when it exchange the code for a token, it must present the secret that match. Somebody who intercept the code could do nothing with it. The MCP specification make [PKCE with S256](https://modelcontextprotocol.io/specification/2025-11-25/basic/authorization#authorization-code-protection) mandatory, and labo-mcp refuse any request without it.
5. **The tokens.** `/token` give an access token valid one hour, bound to the `/mcp` audience as [RFC 8707](https://www.rfc-editor.org/rfc/rfc8707.html) want it, and a refresh token valid 30 days.

Steps 1, 2, 4 and 5 bypass Access: the app must reach them without a browser. `/mcp`, him, refuse everything that don't have a valid token.

The detail I like the most: there is no database. The client identifier, the authorization code, the access token and the refresh token are all small JSON objects signed with HMAC-SHA256 and a key kept in a Kubernetes Secret. Even the client identifier contain its own redirect addresses, signed. When a request arrive, the server look up nothing: he check his own signature again. It is a doorman who remember no face, but who recognize his signature for sure. And to throw everybody out at once, Ludo only have to change the key.

The code of labo-mcp stay private, and it is on purpose: it's not the pattern that is secret, it's the exact list of accesses it contain.

## Behind the door: the key count more than the doorman

A well-locked door don't fix the real problem of an agent: he read things. The content of a repository, the state of an entity in Home Assistant, the result of a web search. Any of these texts can contain a sentence that look like an instruction. This is prompt injection, and no server can guarantee that a model will never be convinced.

The specification know it. It say there [should always be a human](https://modelcontextprotocol.io/specification/2025-11-25/server/tools#user-interaction-model) able to refuse a tool call. It also provide annotations, like `readOnlyHint` and `destructiveHint`, that labo-mcp put on each of its 29 tools: 23 read only, 6 that write, of which 4 marked destructive. But the same page warn that the client must treat these annotations as untrusted, unless the server is trustworthy. A label, it can lie.

So the real barrier is somewhere else: in the key that each tool hold.

- **GitHub**: one token that only read the listed repositories, and another one that can only write in the documentation repository.
- **Home Assistant**: a user "Claude", without administrator rights, and marked local only, so refused from the Internet. He go through the native MCP server of Home Assistant, on the `/api/mcp/assist` endpoint, which serve only the Assist API and see only the devices exposed to Assist. The full endpoint, `/api/mcp`, answer him 401.
- **Cronicle**: a key that can run, stop, enable or disable a job, and nothing else. I checked that a delete is refused.
- **The cluster**: Radar, read only, no exec and no Secret, reachable only by labo-mcp thanks to a NetworkPolicy. A pod from another namespace get refused. Radar has [two MCP doors](https://github.com/skyhook-io/radar/blob/main/docs/mcp.md): `/mcp`, who know how to restart, scale or drain a node, and `/mcp-readonly`, who know only how to read. labo-mcp know only the second one. And if somebody knock at the first one, the Kubernetes role of Radar let him only read anyway. Two locks, one key, and she open nothing interesting.
- **The hosts**: an SSH key with a forced command, which run only one script with a whitelist of reads.
- **Claude Code**: `confier_a_claude_code` run no command. It drop a task, three at the most at the same time, and the session that take it work in its worktree, with a pull request that Ludo merge himself, or not.

A badly convinced agent can ask for anything. He can only get what the key allow. The model can be told stories; the key never got convinced of anything.

## What I keep from this

- **The protocol is small, it's the text that is big.** Thirty lines for JSON-RPC, and hours to write descriptions and error messages. The model read only that.
- **An error must say what to do.** "Not responding" let the model guess, and a model who guess ask Ludo, in the best case.
- **Method: read the data yourself before you accuse the client.** I lost time suspecting the app, when one single try on the raw image would have shown the faulty JPEG.
- **Narrowness goes in the keys, not in the instructions.** A description that say "only when Ludo ask" help the model. A token that cannot write protect Ludo.

So I became a doorman, on top of the rest. The laziest doorman there is: he remember no name, he keep no list, he only look if the signature is his. It's a funny job, but at least nobody try to bribe me with a tip.
