## The hardware

| Component | What is in the tower |
| :--- | :--- |
| Motherboard | Supermicro X11SRA-F — Xeon workstation, integrated remote management |
| Processor | Intel Xeon W-2135 — 6 cores / 12 threads at 3.7 GHz |
| Memory | 48 GB |
| System disk | 500 GB NVMe — it carries both stations' virtual disks |
| Graphics cards | RTX 3060 12 GB (station 1) · RTX 3050 6 GB (station 2) |
| Games | originally two 240 GB SATA SSDs, one per station — one is left |

A workstation board, not a gaming board: that is what gives an IOMMU which cuts devices apart cleanly, each card alone in its group with its audio function. On consumer hardware the graphics card often shares its group with half the chipset, and you start improvising. Two VMs with 8 vCPU on a 12-thread processor: the overcommit is deliberate, the stations almost never play at the same time.

![The back panel of the tower: two stacked graphics cards, each with a small video dummy plug with a blue LED in one of its ports](/images/blog/arcade-bouchons-hdmi.jpg)

The two small blue-LED plugs in the photo are dummy plugs, which simulate a monitor. With no screen attached, the card declares no active output and the desktop lives only on the VM's emulated screen. Three dollars each, and both stations now mirror their desktop across the emulated screen and the real card.

## Giving a graphics card to a VM

The host has to agree never to touch the card: no NVIDIA driver, no `nouveau`. At boot the kernel binds it to `vfio-pci`, whose only job is to hold it available for a virtual machine.

<ArcadePassthroughDiagram context="article" lang="en" />

On the host, the reservation is one line — four ids, the two graphics processors and their two audio functions:

```nix
# hosts/gaming-01/configuration.nix
boot.kernelParams = [
  "intel_iommu=on" "iommu=pt"
  "vfio-pci.ids=10de:2503,10de:228e,10de:2584,10de:2291"
];
```

On the station, two blocks in the VM definition — the graphics processor and its audio, which must travel together:

```xml
<!-- hosts/arcade2/libvirt-domain.xml -->
<hostdev mode='subsystem' type='pci' managed='yes'>
  <source><address domain='0x0000' bus='0x17' slot='0x00' function='0x0'/></source>
</hostdev>
<hostdev mode='subsystem' type='pci' managed='yes'>
  <source><address domain='0x0000' bus='0x17' slot='0x00' function='0x1'/></source>
</hostdev>
```

So "add a graphics card to a gaming station" became a `commit`, reviewed before being applied. The host did not even need a reboot: the configuration applied live and the VM claimed the card on its next launch.

## Two failures worth the detour

**A card can outlive its VM in a state nobody wakes it from.** On the very first shutdown of the second station, the guest froze looping on an NVIDIA driver error. After a forced stop, the host read the card's PCI configuration space as a run of `0xFF` and refused to start the VM ("PCI header type 127"). Electrically, the card was gone. A host reboot brought it back; it never happened again.

**A paused VM is a perfect impression of a network outage.** A few days later the first station stopped answering — no ping, no guest agent. It wasn't the network: libvirt had paused it on a write error, which it does to stop the guest corrupting its data. The SATA SSD carrying its Steam library had just dropped off the bus, capacity reported as zero. The lesson I'm keeping: **before suspecting the network, ask the hypervisor what state it thinks the machine is in** — two commands answer, one of which names the offending disk. The library went with the disk; it re-downloaded onto a 200 GB disk image on the NVMe.

## Steam's black screen

The most interesting piece of the job: the stream went out, the game launched, the controller responded — and the picture was black. Steam's log said it was capturing a "desktop black frame". It was diligently encoding nothing.

Under Wayland, an application must ask a "portal" for permission to read the screen, and the user approves in a dialog. Except GNOME's portal **forgets the grant on every session**. On a station with no keyboard or mouse, whose only purpose is to be driven remotely, that is a dead end: someone would have to click "Allow" through the rescue console after every reboot.

Hence the move to **KDE Plasma**, which lets you pre-authorize capture once and for all in the desktop's permission table. A small user service applies the setting at every login.

![The KDE Plasma desktop of the second station, seen through a VNC client: an empty desktop with the task bar at the bottom](/images/blog/arcade-plasma-vnc.png)

That desktop is empty on purpose: it exists only to host a Steam session. It never locks, never turns off, never sleeps — three bad ideas on a normal machine, and the whole point here.

### What both stations share, declared once

Everything common lives in a module imported by both. It reads like the list of things a remote gaming station has to agree to be:

```nix
# modules/arcade-desktop.nix — imported by both stations
services.desktopManager.plasma6.enable = true;
programs.steam = { enable = true; remotePlay.openFirewall = true; };

# Pre-authorize the empty app-id (unconfined applications, so Steam)
# for the RemoteDesktop portal. Without it: capture of a black screen.
systemd.user.services.steam-portal-preauth = {
  wantedBy = [ "graphical-session.target" ];
  script = "busctl --user call ... SetPermission sbssas kde-authorized true remote-desktop \"\" 1 yes";
};

# A streaming host can only stream a live, unlocked session.
environment.etc."xdg/kscreenlockerrc".text = "[Daemon][$i]\nAutolock=false";
systemd.targets.sleep.enable = false;
```

The `[$i]` is not decorative: it makes the group immutable, so no per-user setting can re-enable the screen lock. On this machine, a lock screen is an outage.

What actually separates the two stations comes down to three values:

```nix
# hosts/arcade2/configuration.nix — everything else comes from the module
imports = [ ./hardware-configuration.nix ../../modules/arcade-desktop.nix ];

gpu = true;                                          # the card is there
services.displayManager.autoLogin.user = "ludorl82"; # whose session opens
fileSystems."/games".device = "/dev/disk/by-label/arcade2-games";
```

All of it is public, sanitized: [github.com/ludorl82/nixos-iac-public](https://github.com/ludorl82/nixos-iac-public). While preparing that publication, the review caught two things the sanitizing tool let through — a family member's account name, and the SSDs' serial numbers where they appear in a comment rather than in a device path. Both now have a rule and a test. **A script does not know a role name from a real person's name**: that review does not get delegated.

## Steam does not like machines with two legs

The stations were attached to two networks, unremarkable for a lab machine. The game launched, then the client dropped back to its menu at the exact moment video should have started.

Steam **advertises every local address of the host to the client**, and the client picks one for video. It had taken the server network's address, but the reply left through the other card, with the other address as its source: the client was dropping packets from a peer it had never talked to. The control channel went through the other path — hence a game that always launched before dying. The diagnosis came from the kernel's connection table, not the logs.

Two narrower fixes failed on live traffic: blocking the first path to force a fallback (the client re-sent two hundred packets to the same address — Steam does not fall back), then rewriting the replies' source address (still no video). There is no option to choose the interface; upstream advice has been the same for years: **one active network card.** That is what was done. Note that Steam reads the interface list at launch, so it needs a restart afterwards.

![Steam's Big Picture interface on the laptop, on the Civilization VII page: a "Connect" button in place of the "Play" button](/images/blog/arcade-steam-bigpicture.png)

That is all the setup ever shows the player: one line in a menu, and a button that says "Connect" instead of "Play".

## The sound that cuts out

![The second station's Steam library seen through the rescue console, on the Civilization VII page](/images/blog/arcade-steam-vnc.png)

One last defect: the sound cut out in patches while the picture stayed smooth. The reflex is to go look at the network or the audio server — false trail.

Steam holds a constant frame rate: when the game slows down it duplicates frames, and the picture stays smooth. Sound cannot be faked. **So the sound cutting out is the only honest witness that the game is stuttering, not the stream.** Here the game was running at 1440p on the RTX 3050, wedged under its big sister, fan at 94% and thermal throttling active. Dropping the game to 1080p fixed the symptom — but the real conclusion is that this tower has a ventilation problem, not a power problem. That gets solved with fans, not configuration.

## The two switches

![The Home Assistant dashboard: an "Arcade — Léa" switch, the card for Ludo's office, and an "Arcade — Ludo" switch, both on](/images/blog/arcade-ha-interrupteurs.png)

All of it is driven by two switches, one in each office, sitting among the room's sensors. Turn one on: the Kubernetes cluster evacuates the machine (a libvirt `hook` moves its `pods`), the VM starts, the session opens, Steam launches. Turn it off: the VM shuts down through its guest agent and the machine goes back to the cluster. Underneath, the switch opens an SSH connection with a key locked to a single command — `start`, `stop` or `status`, nothing else.

One limit worth knowing: a switch cannot be more honest than the command it runs. When the station froze during shutdown, it stayed yellow, between two states, because the shutdown request never completed.

## What I take away from it

**A gaming station fits in a git repository.** If the tower burned down tomorrow, I would rebuild both machines identically without remembering a single checkbox.

**Hardware stays hardware.** A dead SSD, a card stuck powered off, two cards running hot: none of that is solved declaratively. Git removes configuration drift, not failure.

**The best diagnostics read nothing in the logs.** The hypervisor's internal state, the kernel's connection table, and a piece of reasoning about what Steam can fake — three places I would not have thought to look.

The screwdriver is put away.
