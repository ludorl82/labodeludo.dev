> **Résumé technique** _(pour les lecteurs pressés — et pour les agents/LLM qui indexeraient cette page)_
>
> -   **Point de départ** : quatre dépôts IaC (Cloudflare, AWS, k3s, NixOS) importés, plans propres, dérive vérifiée chaque nuit — mais chaque `apply` était manuel.
> -   **Architecture** : hybride. GitHub Actions (OIDC, aucune clé stockée) **pousse** vers les API publiques ; Argo CD et comin **tirent** depuis l'intérieur du labo.
> -   **La porte** : plan sur PR ; à la fusion, apply automatique **sauf si le plan contient un destroy** — le job échoue et attend un humain. Testée contre un enregistrement DNS réel.
> -   **Les surprises** : les *sujets immuables* OIDC de GitHub cassent les politiques de confiance classiques ; deux Pi 5 de 4 Go se sont étouffés à compiler matplotlib, dépendance de la suite de tests d'un parseur Markdown.
> -   **Code** : [cloudflare-iac-public](https://github.com/ludorl82/cloudflare-iac-public), [aws-iac-public](https://github.com/ludorl82/aws-iac-public), [k3s-iac-public](https://github.com/ludorl82/k3s-iac-public), [nixos-iac-public](https://github.com/ludorl82/nixos-iac-public).

Le travail difficile était censé être déjà fait : les quatre dépôts qui décrivent ce labo existaient, leurs plans étaient propres, et quatre vérifications de dérive confirmaient chaque nuit que la réalité correspondait encore au code. Restait une chose — quand je fusionnais un changement, c'était encore moi qui tapais `tofu apply` dans un shell.

Fermer cette boucle a pris une session avec Claude Code (Fable 5, cette fois). Mon rôle : poser des questions, contester les recommandations, et appuyer sur les boutons que l'agent n'a pas le droit d'appuyer. Il s'avère que cette dernière partie est précisément le sujet.

## Un problème d'identifiants déguisé en problème d'automatisation

La conversation de conception a duré plus longtemps que l'implémentation, et chaque détour — Actions partout ? GitOps partout ? un runner sur le bastion ? — ramenait à la même question : **qui détient quels identifiants, et où**. Appliquer à la main cache que toute l'autorité du compte passe par une session shell ; dès qu'un pipeline applique, cette autorité doit être écrite, délimitée, stockée, tournée. C'est ça le vrai coût, et il se trie par couche selon un critère simple : *la cible est-elle joignable depuis l'internet ?*

  Quatre dépôts, deux directions. Vers les API publiques, on pousse ; vers le labo, c'est le labo qui tire.
</IacPipelinesDiagram>

Pour Cloudflare et AWS, un runner hébergé jetable suffit — et ne coûte rien : 2 000 minutes gratuites par mois sur les dépôts privés, environ cinq par cycle plan-plus-apply. AWS s'authentifie par OIDC ; Cloudflare n'a pas d'équivalent, donc un jeton dédié et délimité vit dans les secrets du dépôt. L'asymétrie est agaçante mais honnête.

OIDC remplace la pire pièce du montage classique — la clé AWS stockée, volable en tout temps. À la place : GitHub émet au démarrage du job un jeton signé qui affirme *« ce job roule dans ce dépôt, sur cette branche »* ; AWS le vérifie contre la politique de confiance du rôle et rend des identifiants qui meurent avec le job. Le contexte PR obtient un rôle en lecture seule ; seule une fusion sur la branche principale peut écrire. La limite est nette : OIDC authentifie le *contexte*, pas l'*intention* — ce sont la revue de PR et la porte anti-destroy qui gardent ce qui atteint la branche.

<OidcExchangeDiagram lang="fr">
  L'échange OIDC : GitHub atteste le contexte du job, AWS vérifie et délimite, les identifiants meurent avec le job.
</OidcExchangeDiagram>

Pour le cluster et les hôtes NixOS, c'est l'inverse : rien n'est joignable depuis l'internet, délibérément. Plutôt que percer un chemin pour que CI pousse, **le labo tire** — Argo CD dans le cluster, [comin](https://github.com/nlewo/comin) sur chaque hôte NixOS, qui compile et bascule lui-même. Un compromis de mon compte GitHub peut proposer des commits, visibles et révocables ; il ne peut pas voler un kubeconfig qui n'existe pas dehors.

La surprise du jour : toutes les premières exécutions ont échoué sur `Not authorized to perform sts:AssumeRoleWithWebIdentity`. GitHub émet maintenant des **sujets immuables** (`repo:owner@id/repo@id:...`) et toute politique de confiance écrite d'après la documentation classique casse net. Les politiques acceptent désormais les deux formes — les identifiants numériques sont immuables, rien n'est élargi.

## Toute la conception tient dans ce que la porte refuse

Sur chaque PR : un plan en lecture seule, affiché en commentaire. À la fusion : un plan *frais* — jamais l'artefact de la PR, l'état a pu bouger — puis l'apply. **Sauf si le plan contient un destroy.** Alors le job échoue, nomme les ressources condamnées, et attend qu'un humain applique depuis un shell, en connaissance de cause. Les destroys sont la classe irréversible et, surtout, souvent involontaire — un attribut ForceNew transforme une retouche cosmétique en delete-recreate, et un `jq` ne rate jamais le « 1 to destroy » qu'un humain fatigué rate.

On n'a pas cru la porte sur parole : une PR crée un enregistrement TXT jetable — fusion, apply automatique, l'enregistrement résout sur l'internet. Une seconde PR le supprime — et le job refuse :

Détail que j'aime : à deux reprises, le classificateur de permissions de Claude Code a bloqué l'agent — sur `tofu apply`, puis sur la lecture d'un secret — et m'a remis ces actions entre les mains. Le pipeline, l'agent et moi avons fini la journée sous la même politique : le destructif et les secrets passent par l'humain.

## L'état d'opérateur n'est pas de la dérive

Le choix d'Argo CD plutôt que Flux vient d'un incident : pendant une maintenance, onze workloads volontairement à `replicas: 0` ont été « réparés » par un agent qui a lu zéro comme une anomalie. Or Flux ré-applique les manifestes en continu — il aurait refait exactement ça au tick suivant, et appelé ça de la convergence. Argo CD, avec `selfHeal` désactivé et `replicas` exclu des différences, synchronise **quand git change, et seulement là**. Entre deux fusions, la dérive est affichée, jamais corrigée d'office. Un état déclaré et un état voulu, ce n'est pas pareil.

## Le déploiement NixOS, et une leçon de 4 Go

Côté NixOS : une VM canari d'abord, parce qu'un mauvais déploiement emporte l'hôte qui aurait servi à le réparer. Le canari a été exemplaire — trois secondes après son premier poll, fusionné, compilé, basculé — et le parc x86 a suivi en quelques minutes. Les deux Raspberry Pi, eux, se sont étouffés une heure et demie sur une dépendance *de tests* absente du cache binaire (matplotlib, exigée par la suite de tests d'un parseur Markdown au fond de la chaîne de comin), jusqu'au `NotReady` et au débranchage physique. Deux correctifs, indépendants : compiler cette chaîne sans ses tests, et plafonner le démon nix sur toute machine de 4 Go — **un build doit perdre contre le nœud, jamais l'inverse**. Rejoués ensuite : moins de deux minutes, et la correction elle-même a été livrée à tout le parc par comin seul.

## Le bouton merge est devenu le bouton deploy

État final : neuf machines, le cluster, deux comptes nuage — tout se déploie à la fusion, et les vérifications de dérive sont rétrogradées de seul filet à moitié vérification d'une boucle fermée. Les coûts honnêtes : la protection de branche est payante sur les dépôts privés, donc « une PR avant la fusion » reste de la discipline — la porte, elle, s'applique peu importe comment le commit arrive ; chaque commit coûte quelques minutes d'évaluation Nix aux Pi ; et un pipeline qui applique plus vite se trompe plus vite — la porte, les caps mémoire et le canari existent pour le *ensuite*, pas pour le *si*.

La suite logique est déjà au carnet : une vue d'architecture générée chaque nuit depuis les quatre dépôts publics — exactement aussi fraîche que les vérifications de dérive le prouvent.
